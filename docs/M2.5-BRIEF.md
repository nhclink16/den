# M2.5 brief: iPhone feasibility spike

Owner: Astra (iOS lane). Runs on the iMac over SSH. Read `~/.claude/skills/fleet/references/ios-remote.md` and `references/imac-codex.md` on this box first, then `docs/DESIGN.md` and `docs/ROADMAP.md`.

Question this answers: does a Tauri 2 shell around the web client give an acceptable iPhone app, or do we go native SwiftUI with the LiveKit Swift SDK for M5? Decide with evidence on a physical iPhone, not the simulator.

## Setup
- `ssh imac` works. Cargo, rustup, node, npm, brew, Xcode 26.6 are there. The iPhone 17 Pro Max is paired to the iMac. Xcode must be signed into Nicholas's Apple developer account; if `security find-identity -v -p codesigning` shows no `Apple Development` identity, stop and tell Fable, do not try to work around it.
- Clone `https://github.com/nhclink16/den` on the iMac under `~/den` if it is not there, and keep it on `main`. Use `gh auth status` there; if it is not logged in, stop and tell Fable.
- Install `cargo-tauri` and the iOS targets (`rustup target add aarch64-apple-ios aarch64-apple-ios-sim`), Tauri's iOS prerequisites, and CocoaPods if Tauri needs it.

## The shell
- `cargo tauri ios init` inside `apps/web`, bundle identifier `dev.nhclink.den`, product name `Den`. Automatic signing with the personal team.
- For this spike the app window loads the hosted client, not a bundled one: point the main window at `https://codexbox.tail44c455.ts.net:4200`. That keeps cookies, CSRF, and the WebSocket origin check working with zero server changes. The iPhone must be on Tailscale. Note this decision and its limits in the notes; bundling comes later.
- Info.plist: `NSMicrophoneUsageDescription`, `NSCameraUsageDescription`, `UIBackgroundModes` with `audio` and `voip`, `NSAppTransportSecurity` untouched (the URL is HTTPS).
- App icon: use `design/logos/astra/01-doorway-d.svg` on a squircle tile `#1b1916` at 1024px, generated with `cargo tauri icon`.
- Build and install to the physical iPhone with `cargo tauri ios build` or via Xcode from the generated project. Native Xcode output is the truth for build results.

## What to test on the phone, and record
For each item write pass, fail, or partial with one sentence of evidence in `docs/M2.5-NOTES.md`:
1. Login, open a room, send a message, receive a live message sent from the CLI on codexbox.
2. Upload a video longer than 30 seconds from Photos; does it play inline and scrub.
3. Push-to-open: kill the app, reopen, session persists.
4. Mic and camera permission prompts appear once and the call joins (needs the M3 voice lane's LiveKit running; coordinate through Fable, and if it is not ready yet, test with `https://livekit.io` demo meet page in the same webview to answer the WebRTC questions).
5. Audio keeps playing with the screen locked for two minutes.
6. Bluetooth headset connect and disconnect mid-call routes audio correctly.
7. An incoming phone call interrupts and the app recovers when it ends.
8. Airplane mode for 20 seconds then off: the call and the WebSocket reconnect.
9. Screen share: receiving a share from a desktop renders; note whether broadcasting from the phone is possible at all in a webview.
10. Cold start time and memory from Xcode's debug gauges.

Do not fix the web client to make tests pass; report what the webview does. If you need a change on the server or client, tell Fable.

End the notes with a one-paragraph verdict: Tauri is good enough for M5, or go SwiftUI, and why. Commit `apps/web/src-tauri` and the notes, push, then stop.
