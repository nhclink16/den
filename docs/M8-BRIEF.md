## 1. Prebuilt binaries and a host installer
- GitHub Actions workflow `.github/workflows/release.yml` triggered by tags `v*`. Jobs: `linux-x86_64` builds `den-server`, `den`, `den-host` and the SPA (`apps/web/dist`) and packages `den-server-linux-x86_64.tar.gz` (server binary, CLI, host, `web/`, `deploy/` scripts) plus standalone `den-host-linux-x86_64` and `den-linux-x86_64`; `macos-arm64` and `windows-x86_64` build `den` and `den-host` only. Attach every artifact, a `SHA256SUMS` file, and a source tarball to the release. Cross-compiling from Linux is fine where it works (`cross` or zig); otherwise use the matching runner. If GitHub-hosted runners are blocked by the account's billing state (M6 notes mention this), say so in the notes and produce the Linux artifacts locally with the same script so the release still exists.
- `deploy/install-host.sh`: `curl -fsSL https://denchat.app/install-host.sh | sh -s -- <code>` detects OS and arch, downloads the matching `den-host` from the latest GitHub release, verifies its checksum, installs to `~/.local/bin` (or `%LOCALAPPDATA%\den` on Windows via a `install-host.ps1` twin), runs `den-host login <code>` then `den-host install`. The server serves both scripts at those paths from `deploy/` so the Settings, Machines panel can show the one-liner with the code filled in. Update that panel to show the curl line (and the PowerShell line under a `Windows` toggle) instead of the cargo line.
- Tag `v0.1.0` and publish the first release. Acceptance: on a clean Debian container on codexbox, the curl one-liner enrolls a host against the public server and a terminal opens. On the iMac over `ssh imac` (it has no Rust needed now), the macOS one-liner does the same and a terminal on the iMac opens in Den. Windows: run the PowerShell installer over `ssh pc` if it is reachable, otherwise document it as untested.
- `deploy/release.sh` should prefer downloading the tagged Linux bundle over building locally when a tag is given, so redeploys from a laptop are possible.

## 2. Offline export and import
- `den-server export <zip>` and `den-server import <zip> --into <data-dir>` subcommands on the server binary, run with the server stopped (refuse if the SQLite WAL is held or the systemd unit is active). The archive contains `den.db` via `VACUUM INTO`, `uploads/` including partial uploads with their state, recordings, and `manifest.json` with archive version, schema version, applied migration checksums, per-file SHA-256 and sizes, instance name, and export time. It excludes `den.env`, host tokens, and anything under `.ssh`.
- Import validates the manifest, rejects path traversal and symlinks, enforces expansion limits, checks integrity and foreign keys, migrates older schemas forward, rejects newer or divergent ones, and installs atomically into an empty target directory. By default it invalidates sessions, tokens, invites, host credentials, and grants, and ends terminal sessions; `--keep-credentials` preserves them for disaster recovery. Prints a summary of what was imported and what was invalidated.
- Tests: one integration test that exports a seeded database with a partial upload and a recording, imports it into a fresh dir, boots the server against it, and checks channels, messages, an upload range request, and that old tokens are rejected. One test for the refusal cases (running server, newer schema, traversal).
- Wire the nightly VPS backup to use `export` instead of the ad hoc `VACUUM INTO` plus rsync, keeping the same destination and retention on codexbox, and rerun `deploy/restore-check.py` against a real export. Document in `docs/M8-NOTES.md`.

The client shows it in the sidebar wordmark, the login card title, the document title, and notifications, everywhere the literal "Den" appears for users.
